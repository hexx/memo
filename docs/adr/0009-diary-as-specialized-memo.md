# 日記はメモの特殊化として表現する（別エンティティにしない）

## Status

Accepted（2026-09-24、日記機能の設計セッション）

## Context

特定の日付に紐づく記録を書く・読み返す「日記」機能の追加を検討した。既存の概念はメモ (Memo) のみで、日付に紐づく属性を持たない。日記のモデル化には (1) 別エンティティ（diaries テーブル新設）、(2) メモの特殊化（日付属性を持つメモ）、(3) テンプレートのみ（日付は本文・タイトル任せ）の選択肢があった。

## Decision

日記は memos の行として表現し、日付属性を持つメモとして扱う（メモの特殊化）。1 日につき最大 1 つとし、専用の日記ビューは「日付を持つメモ」を日付順に並べたフィルタ済みビューとして位置づける。

## Rationale

- 検索・ラベル・ピン・アーカイブ・AI 自動タイトル・org インポート/エクスポートなど既存資産がそのまま日記にも効く
- 別エンティティにすると、これらの機能を日記用に再実装するか、メモと横断する仕組みを新設する必要があり、単一ユーザー向けの小さなアプリに見合わない
- テンプレートのみ（日付をデータとして持たない）では、日付による一覧・参照・一意性（1 日 1 つ）を表現できない

## Consequences

- ホーム（メイン一覧）では日記を表示しない（検索・ラベルフィルタを含む）。日記ビューには日記の一覧・検索・ラベルフィルタを置き、アーカイブ画面は日記を含む全メモを表示する。日記ビューはアーカイブ済みを既定で非表示とする
- 日記かどうかの判定・並び替えは日付属性に基づく。日記ビューはメモ一覧の絞り込みビューである
- 日記固有のデータ（日付カラム等）の詳細は後続の設計で決定する

## Considered Options

- **別エンティティ（diaries テーブル新設）**: 日記固有機能（カレンダー、連続記録など）を伸ばしやすいが、既存機能の再実装/共有が必要。不採用
- **テンプレートのみ**: 実装は最小だが、日付が本文任せになり一覧・検索・一意性を担保できない。不採用
- **ラベル方式（「日記」ラベル + 日付タイトル）**: 日記かどうかはユーザー定義の整理軸（ラベル）ではなくメモの属性の責務。不採用
