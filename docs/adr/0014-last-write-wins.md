# 同一メモの同時編集は last-write-wins とする（楽観ロックを入れない）

## Status

Accepted（2026-10-11）

## Context

`PUT /memos/:id` は本文を**まるごと置換**する。単一ユーザーの PWA だが、同じメモを複数のタブや端末で開くことは起こりうる。オートセーブ（ADR 0013）の導入で書き込み頻度が上がり、衝突の機会も増える。

## Decision

競合の検知・通知・マージは行わず、**後から書いた側が全面勝ち（last-write-wins）**とする。`updatedAt` を使った楽観ロック（読み取り時のバージョンを送り、一致しなければ 409）は導入しない。

## Rationale

- 衝突の当事者は実質「自分」であり、古い方の内容が意図せず残るより、直前の操作が勝つのが自然
- 楽観ロックにはバージョンの受け渡し・409 の UI・再読込やマージの導線が必要で、単一ユーザーの用途に対して対価が見合わない
- オートセーブは失敗経路が増えるほど価値が下がる。409 を足すと「保存に失敗」の原因が入力と無関係な競合になり、ユーザーが自力で回復できなくなる
- 明示的に last-write-wins と決めておくことで、暗黙の仕様を将来の実装者が楽観ロックだと誤解しない

## Consequences

- 片方のタブでの編集が、もう片方の未保存の編集を検知なしに上書きしうる
- マルチユーザー化する場合は本 ADR を supersede してロックの導入を再検討する

## Considered Options

- **`updatedAt` を楽観ロックに使う**: スキーマ変更なしで実現できる（既存列をバージョン代わりにする）が、409 時の UI とリトライ設計が必要
- **タブ間ロック（BroadcastChannel / localStorage）**: 同一端末のタブしか守れず、機構だけが増える
- **フィールド単位のマージ**: 本文は構造化されていない生のテキストであり、自動マージは現実的でない
