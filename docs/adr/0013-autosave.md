# 編集の無操作を契機に自動保存する（オートセーブ）を導入する

## Status

Accepted（2026-10-11）

## Context

本アプリの保存は明示操作のみだった。

- `/memos/:id`（メモ詳細/編集画面）は「保存」ボタンを押して初めて `PUT /memos/:id` が飛ぶ
- ホーム/日記の新規作成ダイアログは「作成」を押すまで `POST` されず、押さずに閉じれば何も残らない

このため、保存ボタンの押し忘れやタブの閉じ忘れで書いた内容が失われる。これが導入の主目的であり、保存操作の手間そのものを削ることは副次的な効果に留める。

制約として、`PUT /memos/:id` は本文・タイトル・ラベル・日付を**まるごと置換**する（部分更新はできない）。`navigator.sendBeacon` は POST 限定なので `PUT` には使えず、`fetch` の `keepalive` はボディに 64KiB の上限を持つ。サーバーは PWA のオフライン閲覧のみ対応し、書き込みのオフライン対応は持たない。

## Decision

1. **対象面**: `/memos/:id`（メモ・日記の両方）と、ホーム/日記の新規作成ダイアログ。アーカイブ画面から開いた詳細も同じ。
2. **契機**: 変更を検知してから 1 秒のデバウンス。保存は直列化し、保存中に来た変更は 1 つにまとめて再送する。
3. **明示的な保存ボタンは残す。** 保存状態（`保存済み` / `保存中…` / `保存に失敗（再試行）`）を保存ボタンと同じ行の左に表示する。
4. **失敗時**は編集内容を未保存のまま保持し、① オンライン復帰時、② 次の変更時、③ 明示的な再試行、の 3 経路で再送する。localStorage 等への下書き退避は行わない。
5. **新規作成**: 内容（本文、または日記の日付の既定値以外のタイトル）が入ったら `POST` してメモを作り、以後は既存メモと同じ `PUT` 経路に合流する。開いただけでは作らない。ダイアログを閉じることは破棄ではなく保存を意味し、破棄手段は用意しない。閉じるときは保留分を送ってから閉じ、保存できなかったときだけ破棄の確認を出す。主ボタンは初回 `POST` の前は「作成」、成功後は「保存」で、有効条件は新規メモが「タイトルか本文が非空白」、新規日記が「日付あり」。
6. **タイトル**: 既存メモではタイトル欄が空のとき `title` を送らない（サーバーは既存タイトルを維持する。空欄時は既存タイトルを placeholder に出す）。新規メモではクライアントが暫定タイトル（本文の先頭行、無ければ「無題」）を決めて `POST` する。AI によるタイトル生成は明示的な「AIで生成」ボタンのみで、オートセーブの経路には入れない。
7. **ラベル・日記の日付の変更も同じデバウンス経路に含める。** 日記の日付重複（409）は自動遷移せず、エラー表示と書きかけの保持でユーザーに委ねる。
8. `updatedAt` はオートセーブでも毎回更新する（一覧は更新降順のため、触ったメモが上に来る）。
9. **削除時は保留中・実行中のオートセーブをキャンセルする。**
10. **離脱時**: 「← 戻る」は flush の完了を待ってから遷移する（失敗したら留まって状態表示に出す）。タブを閉じる・バックグラウンドに回す場合は `visibilitychange`(hidden) で通常の `fetch`、`pagehide` で `keepalive: true` の `fetch` を使う。SPA の画面遷移によるアンマウントでは通常の `fetch` を投げる。64KiB を超えるメモでは `keepalive` の flush が失敗しうる（非保証）。`beforeunload` の離脱警告は出さない。
11. サーバー API・DB スキーマ・マイグレーションの変更は不要（既存の `PUT` の「`title` 省略＝既存維持」分岐と `POST` で足りる）。

## Rationale

- **1 秒のデバウンスと離脱 flush の併用**: デバウンスだけでは「書いた直後に閉じる」が穴になる。逆に入力のたびの即時保存は全置換 PUT に対して過剰。1 秒なら通常の停止でほぼ確実に保存され、離脱 flush は最後の 1 秒を救う保険になる。blur 契機は TipTap のツールバー操作で頻繁に発火し、体感が安定しないため採らない。
- **保存ボタンを残す**: オートセーブは保険であり、明示操作を奪わない。状態表示が無いと「保存できていないのに保存済みに見える」という最悪の失敗モードになるため、状態表示とセットで導入する。
- **localStorage の下書きを持たない**: 実装とテストが重く、PWA の「オフライン書き込み非対応」という既存方針を覆すことになる。未保存の内容を画面上に保持して可視化するだけでも「押し忘れ」という主目的は満たせる。
- **AI タイトルを経路に入れない**: 入れると入力を止めるたびに LLM 呼び出しが走り、レイテンシと課金が入力に連動する。さらにサーバーはタイトルを解決できないと 400 を返すため、**AI の失敗が保存の失敗に直結する**。AI は明示ボタンに残す。
- **新規作成も対象にする**: 「保存を押さずに閉じる」事故が最も多いのは新規作成である。ID が無い状態のための別機構（ローカル下書き）を足すのではなく、内容が入った時点で `POST` して既存メモの経路に合流させるのが最小。
- **破棄手段を用意しない**: 「保存されているから破棄手段は不要」という整理であり、その前提が崩れる唯一の場合（初回 `POST` 未成功）にだけ確認を出す。
- **戻るを待たせる**: dirty はコンポーネントの寿命とともに消えるため、離脱時に失敗したことを可視化できない。数 100ms の遷移の遅れより、二度と気づけない損失の方が重い。

## Consequences

- 保存状態の表示と、デバウンス・直列化・リトライを担うフックが必要になる。
- `initialMemo` の同期（別メモへの切り替え）をユーザー編集と誤認しないガードが要る（同期 → 保存 → 再取得のループを避ける）。
- `["memos"]` は `staleTime: 30_000` のため、詳細画面を離れるとき・新規ダイアログを含む画面を離れるときに invalidate する。保存のたびには invalidate しない（編集のたびに全件取得が飛び、新規ダイアログでは背後の一覧が組み替わるのが見えるため）。`["memo", id]` はサーバーがタイトルを解決する余地が無いため、オートセーブ経路では再取得不要。
- `DELETE` と `PUT` の順序が入れ替わっても、`PUT` は UPSERT ではないのでメモが復活することはない。
- `docs/design.md` にオートセーブの節を追加し、ADR 0006 のテスト原則に fake timers の利用を追記する。

## Considered Options

- **新規作成を対象外にする**: ID が無いことによる特別扱いを避けられるが、押し忘れの事故が最も多い面を救えず主目的を満たさない。
- **localStorage に下書きを退避する**: オフラインでも書けるが、既存の「オフライン書き込み非対応」方針を覆し、復元タイミング・競合・テストの対価が大きい。
- **タイトルが空の間はオートセーブしない**: タイトルを書かない人を救えない。
- **入力のたびに即時保存する**: 全置換 PUT に対して過剰。
- **破棄ボタンや確認ダイアログを常に出す**: オートセーブの利点（押さなくてよい）を打ち消す。
- **`beforeunload` の離脱警告を出す**: 自動保存と矛盾する。
